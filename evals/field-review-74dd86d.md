## §1 BaseSampleTime snapping

Setup:
- The PLC channel is `prog1.counter` (a test counter in the program on the motion task) (LREAL,
  +1.0 per cycle) on port 851. It was added for this test and runs on the motion PLC task,
  **4 ms** (the fastest PLC task).
- The NC channel is `Axes.axis1.SetPos` on port 501. The NC SAF task runs at **2 ms**. The 1 ms
  task the brief asked for does not exist, so the cases were adapted to 4 ms/2 ms.
- Files are `ST-a` … `ST-e.tcscopex`, generated by `newscope` from `minimal-single-channel`, with
  30 s record time and `UseTaskSampleTime=false` on both acquisitions (verified in the file).
- `checkscope --tmc` reports ok on all five, and the counter resolves as compiled type LREAL.

**Rule, as measured (d, c, b, plus e as control):** Scope snaps the sample time **when it starts
recording**, not on load or Save. Each acquisition is snapped to the cycle of **its own task**:
PLC 4 ms, NC 2 ms, independently within one file. It **rounds down** to a whole multiple of that
cycle (d: 7.5 → 4 on PLC, 7.5 → 6 on NC; the NC value discriminates, since nearest would give 8).
A value **below one cycle becomes one cycle** (b: 0.5 → 4 / 2; c: 3 → 4 on PLC). Exact multiples
are kept (e; c on NC: 3 → 2 = floor). No message was shown in any case.
This fits the earlier 10 → 8 ms on a 4 ms task.

a (1 tick = 100 ns) behaves like b: Scope accepted it without a message and recorded one cycle
per task, 4 ms / 2 ms. It ran 30 s with 0 gaps and the counter stepped +1 on all 7499 intervals.
The "~20000000 samples/s" load warning from `checkscope` is therefore a nominal figure. The real
load was 250 + 500 samples/s.

e, Save: the file was added to the Measurement project and Save was pressed. `ST-e.tcscopex` was
**not rewritten**: mtime is unchanged from generation, and BaseSampleTime is still 80000/80000.
Only the `.tcmproj` changed. Save on an unmodified scope does not re-serialise it, so a "value
after Save" needs Scope to regard the file as dirty.
A second Save, after the user was asked to toggle a property, also left the file untouched.

e, Properties grid (the counter): Sample Time [ms] **8**, UseTaskSampleTime "Free Sampletime",
DataType REAL64, Target Port 851, Symbol based True. This matches what was written.

e, Save after editing Record Time and setting it back: the file **was rewritten** (27146 → 39272
bytes). BaseSampleTime is still **80000 / 80000**, UseTaskSampleTime false, both REAL64, ports
851/501, and `checkscope` is ok at 125 Hz / 125 Hz. So editing and reverting a property is what
makes Scope write the file.

e, Record: the user recorded, but **the recorded data was discarded when the scope's settings
were changed afterwards**. Save the `.svdx` before touching any setting. Record again.

e, second Record: `ST-e.svdx`. The `.tcscopex` was not modified by Record, still 80000 / 80000.
`manifest` after `ingest`: 125.0 Hz on both groups (8.0 ms declared = measured). PLC 3750
samples over 29.992 s, NC 3751 over 30.0 s, 0 gaps, max skew 4 ms. The counter step is **+2.0 on
all 3749 intervals**, which is 8 ms / 4 ms cycle and confirms the rate independently of the
timestamps. SetPos is constant (axis not moving), which is fine for a rate test.

d, Save (Properties not read beforehand): the file was rewritten (39147 bytes). BaseSampleTime is
still **75000 / 75000**, UseTaskSampleTime false, and RecordTime 30 s is intact. **Save does not
snap 7.5 ms**, on either the 4 ms PLC task or the 2 ms NC task.

Note: `manifest` refuses a raw `.svdx` and names `ingest` as the fix. That is correct, and the
skill's workflow says the same.

Observation from the tool: case a is accepted by both `newscope` and `checkscope` (no problem).
Only the load warning fires, at "~20000000 samples/s", which takes 100 ns literally.

## §3 `events` -- standing following error, few-valued channels

All three recordings were re-ingested from `.svdx` with 74dd86d. B1 and B1b are the Part B axis
from the last round (not one of R3's axis1-3). Each has SetPos and PosDiff of the same axis, so
`standing` can run. R3 has axis1's SetPos.

- **B1b (end stop):** exactly **one** `standing` on PosDiff, setpoint `SetPos`. It starts at
  **13.244 s** and lasts 13 378 samples at 2 ms = **26.76 s**, severity 26.756. This matches the
  expectation (≈13.2 s, ≈27 s). The other events: 41 ramp, 11 step, 5 hold, 4 spike (62 total,
  no clipping).
- **B1 (software limit): one `standing`, where none was expected.** It is on PosDiff from
  **7.312 s**, 1137 samples = 2.27 s, severity 2.274, value −0.031, setpoint SetPos. It ranks last
  of 57. This is the moment the axis arrives at the limit. SetPos reaches its final value in
  7.3-9.6 s and SetVelo drops to 0. PosDiff then **decays** from about −0.03 through −0.02 to
  −0.008, and by 12 s sits within ±0.01 of 0. It is a settling tail of the position loop, not an
  error held against an obstacle. Over the flagged 2.3 s there were 104 distinct values, drifting
  toward zero. Verdict: **a mild false positive**. It is ranked last and its severity is 12×
  below B1b's, but it is reported. A decay test (does |PosDiff| shrink across the span?) or a
  minimum duration of several seconds would separate the two.
- **R3:** **no `clipping`** anywhere. The near-two-valued PLC REAL64 rate now reports 14
  flatline + 11 step, where the last round had clipping max 57.8 % / min 40.9 %. **No
  `standing`** on axis1's PosDiff, or on any channel. The 228 s idle after the stop is **not**
  flagged standing. It appears as a PosDiff `flatline` of 114 062 samples from 277.966 s, which is
  right: the axis is idle, not held off target.
